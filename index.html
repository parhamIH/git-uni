G

Git

یک سیستم کنترل نسخهٔ توزیع‌شده است. بخش مهمی از تاریخچه و عملیات را روی رایانهٔ خودت انجام می‌دهی؛ اینترنت برای هر Commit لازم نیست.

GH

GitHub

سرویسی برای میزبانی مخازن Git و همکاری تیمی؛ امکاناتی مثل Pull Request، Issues، Code Review و GitHub Pages دارد.

نکتهٔ ارائه

Git و GitHub یکی نیستند. می‌توان Git را بدون GitHub به کار برد؛ اما GitHub از Git برای همکاری و میزبانی استفاده می‌کند.

سه واژه که مرتب می‌شنوی

Repository (Repo)

مخزن پروژه و داده‌های تاریخچهٔ آن.

Commit

یک نقطهٔ ثبت‌شده در تاریخچه، همراه پیام و اطلاعات نویسنده.

Branch

اشاره‌گری سبک به یک Commit؛ مسیر مستقلی برای پیش‌برد کار.

بحث کلاسیاگر فایل‌های پروژه را با نام‌های v1، v2 و final نگه داریم، چه چیزهایی را از دست می‌دهیم؟

از کلاس بخواه مثال بزنند: مقایسهٔ دقیق تغییرها، دلیل هر تغییر، اتصال کار به نویسنده، یا ترکیب امن کار چند نفر.

اصطلاحات این فصل

VCS یا Version Control System یعنی سیستم کنترل نسخه. SCM معمولاً مخفف Source Code Management یا Source Control Management است و در گفت‌وگوی روزمره برای این دسته ابزارها استفاده می‌شود. CVCS یعنی Centralized VCS که یک سرور مرکزی محور اصلی تاریخچه است؛ DVCS یعنی Distributed VCS که توسعه‌دهندگان مخزن محلی و تاریخچه دارند. Git یک DVCS است.

نکتهٔ مهم دربارهٔ git add

فصل 05 / بررسی تاریخچهGit۷ دقیقه

Diff، Patch، Log و Show؛ از حدس به شواهد

این ابزارها به تو نشان می‌دهند چه چیزی تغییر کرده، چه چیزی قرار است Commit شود و یک Commit دقیقاً چه محتوایی دارد. پیش از Commit و هنگام Code Review از آن‌ها استفاده کن.

یک Diff ساده را بخوانیم

فرض کن نسخهٔ قبلی فایل hello.py این بوده و فقط متن خروجی را تغییر می‌دهی:

قبل
def greet(name):
    return f"Hello, {name}!"
بعد
def greet(name):
    return f"Welcome, {name}!"
diff --git a/hello.py b/hello.py
index 1a2b3c4..5d6e7f8 100644
--- a/hello.py
+++ b/hello.py
@@ -2 +2 @@ def greet(name):
-    return f"Hello, {name}!"
+    return f"Welcome, {name}!"
− خط حذف‌شده یا نسخهٔ قبلی+ خط افزوده‌شده یا نسخهٔ جدید@@ محدودهٔ تقریبی تغییر در فایل

هر خط با - نسخهٔ قبلی و هر خط با + نسخهٔ جدید را نشان می‌دهد. Patch معمولاً همین تفاوتِ قالب‌بندی‌شده به‌همراه اطلاعات مسیر و زمینه است؛ نه یک Commit کامل به‌تنهایی.

git show برای یک Commit معمولاً پیام و اطلاعات آن و Diff تغییرهایی را که همان Commit معرفی کرده نمایش می‌دهد. --stat خروجی را به آمار فایل‌ها خلاصه می‌کند. اگر شناسه ندهی، معمولاً شیء فعلی مانند HEAD را نمایش می‌دهد.

Diff را به Patch فایل تبدیل کن و آن را اعمال کن

این نمونه دوطرفه است: در مخزن مبدأ یک Patch تولید می‌کنی و آن را به هم‌تیمی یا مخزن دیگری منتقل می‌کنی که هنوز همان تغییر را ندارد.

# در مخزن مبدأ: تغییرهای unstaged را ذخیره کن
git diff > welcome.patch

# یا نسخهٔ Stage شده را ذخیره کن
git diff --staged > staged.patch

# فایل welcome.patch را به مقصد منتقل کن؛ در مخزن مقصد:
git status
git apply --check ../welcome.patch
git apply ../welcome.patch

git status
git diff
دو ابزار متفاوت برای دو نیاز

git diff تفاوت را تولید می‌کند؛ git apply Patch را روی فایل‌ها اعمال می‌کند، اما به‌تنهایی Commit نمی‌سازد. برای بسته‌بندی Commit همراه اطلاعات آن، git format-patch وجود دارد و معمولاً با git am اعمال می‌شود؛ این روش را با Patch سادهٔ git diff یکی ندان.

# نمونهٔ جریان اشتراک‌گذاری یک Commit
git format-patch -1 HEAD
# روی مقصد، فایل خروجی را اعمال و Commit کن
git am 0001-*.patch

اگر همین Patch را دوباره روی همان Working Treeای که تغییرها از آن ساخته شده‌اند اعمال کنی، معمولاً به‌دلیل وجود تغییرها قابل اعمال نخواهد بود. در مقصد باید نسخهٔ پایه سازگار باشد. Patch متنی برای فایل‌های متنی مناسب است؛ پیش از اعمال آن، وضعیت مخزن را بررسی کن.

فصل 06 / وضعیت فایل و بازگردانیGit۸ دقیقه

هر فایل دقیقاً در چه وضعیتی است؟

Git وضعیت را برای هر فایل می‌سنجد؛ در یک لحظه بعضی فایل‌ها می‌توانند Stage باشند و بعضی دیگر Modified یا Untracked. git status راه اصلی برای فهمیدن همین وضعیت است.

Untracked / Modifiedفایل جدید است یا نسخهٔ tracked تغییر کردهgit add
←
Stagedنسخهٔ انتخاب‌شده برای Commit بعدیgit diff --staged
←
Committed / Cleanپس از Commit فایل tracked با وضعیت ثبت‌شده هماهنگ استgit commit

پس از حالت Clean، ویرایش دوباره فایل آن را Modified می‌کند. اگر فایل هنوز Untracked است، Git محتوای آن را تا وقتی Stage نشود در Diffهای معمول trackedها وارد نمی‌کند.

وضعیت/اصطلاحتوضیحدستور کمکی

git add -A یا git add -p؟

git add -A

همهٔ تغییرهای قابل Stage در محدودهٔ مخزن را هماهنگ می‌کند: فایل‌های جدید، ویرایش‌ها و حذف‌ها. فایل‌های نادیده‌گرفته‌شده معمولاً اضافه نمی‌شوند.

git status
git add -A
git status
git diff --staged

کاربرد: وقتی تمام تغییرها را مرور کرده‌ای و واقعاً می‌خواهی همه‌شان در Commit بعدی باشند.

git add -p

تغییرها را به تکه‌های کوچک‌تر (hunk) نشان می‌دهد تا انتخاب کنی کدام بخش Stage شود؛ برخلاف git add file.py که همهٔ تغییرهای فعلی آن فایل را Stage می‌کند.

git add -p app.py
# y = stage this hunk
# n = skip this hunk
# s = split hunk (if possible)
# q = quit

کاربرد: وقتی دو تغییر مستقل در یک فایل داری و می‌خواهی دو Commit تمیز و جدا بسازی.

git commit -a -m را بشناس

git commit -a -m "fix: validate empty input"

گزینهٔ -a محتوای تغییرکرده و حذف‌شدهٔ فایل‌های از قبل Track شده را برای Commit Stage می‌کند و سپس Commit می‌سازد؛ فایل‌های Untracked جدید را وارد نمی‌کند. برای دیدن کنترل دقیق تغییرها، معمولاً git add و سپس git commit -m شفاف‌ترند. پیش از Commit، git status و git diff را ببین.

تغییرنام فایل با git mv

git mv old_name.py new_name.py
git status
git diff --staged --summary
git commit -m "refactor: rename parser module"

git mv فایل را جابه‌جا یا Rename می‌کند و Index را هم به‌روزرسانی می‌کند؛ بعد هنوز باید Commit انجام شود. دستور معمول سیستم‌عامل مثل mv یا تغییرنام در File Explorer هم مجاز است، اما آن روش به‌تنهایی Stage کردن را انجام نمی‌دهد و باید تغییر حذف/افزوده‌شدن را جداگانه با Git مدیریت کنی. Git Rename را در تاریخچه عمدتاً بر اساس شباهت محتوا تشخیص می‌دهد؛ نام ابزار جادو نیست.

checkout، switch، restore و reset

git switch main

شاخهٔ جاری را عوض می‌کند.

git checkout -b feature/search

روش کلاسیک برای ساخت شاخه و رفتن به آن؛ امروزه git switch -c واضح‌تر است.

git restore file.txt

تغییر unstaged فایل را با نسخهٔ Index جایگزین می‌کند؛ ممکن است تغییر محلی را از بین ببرد.

git restore --staged file.txt

فایل را از Stage خارج می‌کند و معمولاً تغییرهای Working Tree را نگه می‌دارد.

git reset file.txt

در شکل دارای path، Index را برای آن فایل به حالت HEAD برمی‌گرداند؛ معمولاً معادل عملی git restore --staged file.txt است و Working Tree را پاک نمی‌کند.

git checkout -- file.txt

شکل قدیمی و مبهم برای بازیابی فایل از Index؛ ممکن است تغییر unstaged را دور بریزد. برای شفافیت git restore را ترجیح بده.

سه اسم شبیه‌اند، اثر یکسان ندارند.

git switch برای شاخه‌هاست؛ git restore برای بازیابی محتوای فایل؛ git reset <file> برای Index. هیچ‌کدام را از روی اسم حدس نزن. قبل و بعد از آن git status بزن، و قبل از حذف تغییر ارزشمند از آن نسخهٔ پشتیبان یا Commit بساز.

اصلاح آخرین Commit با --amend

# تغییرهای Stage شده را به آخرین Commit اضافه کن
# یا پیام آن را اصلاح کن
git add README.md
git commit --amend

# اصلاح پیام فقط؛ بدون باز کردن editor
git commit --amend -m "docs: clarify setup instructions"

# اگر فقط می‌خواهی پیام قبلی حفظ شود
git commit --amend --no-edit

--amend آخرین Commit را با یک Commit جدید جایگزین می‌کند؛ Commitها تغییرناپذیرند، بنابراین شناسهٔ Commit عوض می‌شود حتی اگر فقط پیام را اصلاح کنی. معمولاً این کار را روی Commit محلی یا شاخه‌ای که هنوز دیگران از آن استفاده نکرده‌اند انجام بده. اگر Commit قبلاً Push و توسط دیگران دریافت شده، بازنویسی آن باعث نیاز به Force Push و هماهنگی می‌شود؛ روی تاریخچهٔ مشترک، اغلب ساختن Commit جدید امن‌تر است.

git commit -s با -S فرق دارد

git commit -s -m "fix: guard empty filename"

گزینهٔ کوچک -s یک خط Signed-off-by: Name <email> به انتهای پیام اضافه می‌کند؛ در بعضی پروژه‌ها برای تأیید منشأ و رعایت Developer Certificate of Origin (DCO) لازم است. این گزینه به‌تنهایی امضای رمزنگاری‌شده نیست. گزینهٔ بزرگ -S برای امضای رمزنگاری‌شدهٔ Commit با کلید تنظیم‌شده کاربرد دارد.

اصل مهم:

یک Commit برای هر تغییر منطقی و قابل توضیح بساز، نه لزوماً برای هر خط. اگر یک فایل هم اصلاح باگ و هم تغییر مستندات نامرتبط دارد، می‌توان با git add -p آن‌ها را به Commitهای جدا تقسیم کرد.

فصل 07 / تاریخچهٔ شاخه‌ایGit۷ دقیقه

Branch؛ قابلیت جدید، بدون ریسک تغییر مستقیم main

برای ساختن قابلیت جدید لازم نیست کار روزمره روی شاخهٔ اصلی انجام شود. Branch یک مسیر کاری جدا می‌دهد که بعداً می‌تواند با main ادغام شود.

main feature/search

دموی کوتاه Branch و Merge

# ساخت و رفتن به شاخهٔ جدید
git switch -c feature/add-intro

# فایل را تغییر بده و ثبت کن
git add README.md
git commit -m "docs: add introduction"

# بازگشت به شاخهٔ اصلی و ادغام
git switch main
git merge feature/add-intro

# دیدن گراف شاخه‌ها
git log --oneline --graph --decorate --all
git branch

شاخه‌های محلی را فهرست می‌کند؛ شاخهٔ جاری با * مشخص می‌شود.

git switch main

رفتن به شاخهٔ موجود؛ اگر تغییرات محلی با جابه‌جایی تداخل داشته باشند، Git ممکن است جلوی سوییچ را بگیرد.

git branch -d feature/add-intro

-d حذف امن شاخهٔ محلی ادغام‌شده؛ برای حذف شاخهٔ Remote، فرمان جداگانه لازم است.

git merge feature/add-intro

شاخهٔ نام‌برده را در شاخهٔ فعلی ادغام می‌کند؛ ابتدا بررسی کن واقعاً روی شاخهٔ مقصد هستی.

چرا Branch می‌سازیم؟

جداسازی کار، امکان Code Review، آسان‌تر شدن همکاری و حفظ تمرکز شاخهٔ اصلی. اسم‌هایی مثل feature/login، fix/cart-total و docs/setup هدف شاخه را مشخص‌تر می‌کنند.

دستورهای Branch که واقعاً لازم‌اند

git branch

شاخه‌های محلی را فهرست می‌کند؛ علامت * شاخهٔ جاری است.

git branch -v

شاخه‌ها را همراه آخرین Commit هرکدام نشان می‌دهد.

git branch -vv

علاوه بر آخرین Commit، اطلاعات upstream و وضعیت ahead/behind را در صورت قابل محاسبه بودن نمایش می‌دهد.

git branch -a

شاخه‌های محلی و Remote-tracking را لیست می‌کند؛ شاخهٔ Remote-tracking کپی محلیِ وضعیت ریموت است، نه خود سرور.

git branch --show-current

نام شاخهٔ جاری را نشان می‌دهد؛ در کنار git status -sb برای جلوگیری از Merge روی شاخهٔ اشتباه مفید است.

git checkout -b feature/search

روش قدیمی‌تر برای ساخت شاخه و رفتن به آن؛ معادل روشن‌تر امروزی: git switch -c feature/search.

git branch -d feature/search

حذف محافظه‌کارانه؛ معمولاً اگر Git شاخه را ادغام‌شده نداند، حذف را متوقف می‌کند.

git branch -D feature/search

حذف اجباری شاخهٔ محلی حتی اگر ادغام نشده باشد. فقط وقتی مطمئنی Commitهای آن دیگر لازم نیستند.

git push origin --delete feature/search

حذف شاخه از Remote؛ با حذف شاخهٔ محلی فرق دارد. ابتدا مطمئن شو تیم هنوز به آن نیاز ندارد.

دو شکل رایج Merge

Fast-forward · FF

فقط جلو رفتن اشاره‌گر

main:    A—B
              \
feature:        C—D

بعد از FF:
main:    A—B—C—D

اگر شاخهٔ مقصد از زمان جدا شدن شاخهٔ دیگر Commit تازه‌ای نداشته باشد و بتوان مسیر را مستقیم جلو برد، Git معمولاً اشاره‌گر را جلو می‌برد؛ Merge Commit جدیدی لازم نیست.

Three-way merge

ترکیب از یک Base مشترک

A——B——E————M  main
     \     /
      C——D    feature
    base: B

وقتی هر دو شاخه بعد از نقطهٔ مشترک Commitهای جداگانه دارند، Git تغییرات دو سر و Base مشترک را بررسی می‌کند و معمولاً Merge Commit با دو والد می‌سازد. اگر تغییرها ناسازگار باشند، ممکن است Conflict رخ دهد.

git merge --ff-only feature/search

فقط وقتی ادغام از نوع Fast-forward ممکن باشد قبول می‌کند؛ در غیر این صورت متوقف می‌شود. برای جلوگیری از Merge Commit ناخواسته روی شاخهٔ ساده مفید است.

git merge --no-ff feature/search

حتی اگر Fast-forward ممکن باشد Merge Commit می‌سازد؛ گاهی برای حفظ مرز یک قابلیت در تاریخچه مفید است.

Rebase؛ به‌روز کردن شاخه و خطی‌تر کردن Log

git rebase Commitهای شاخهٔ فعلی را طوری دوباره اعمال می‌کند که از نوک یک Base جدید ادامه پیدا کنند. این کار می‌تواند تاریخچهٔ Branch شخصی را خواناتر و دنبال‌کردن تغییرها را ساده‌تر کند؛ اما Commitهای بازنویسی‌شده شناسهٔ جدید می‌گیرند.

قبل از Rebase
A——B——E  main
    \
     C——D  feature
شاخه‌ها از B جدا شده‌اند.
→
بعد از Rebase
A——B——E——C'——D'  feature
         main
C و D دوباره اعمال شده‌اند؛ C′ و D′ شناسه‌های جدید دارند.
# وضعیت محلی را بررسی کن و اطلاعات Remote را تازه کن
git status
git fetch origin

# روی شاخهٔ شخصی خودت باش
git switch feature/search
git rebase origin/main

# اگر Conflict شد: فایل را حل و Stage کن
git add path/to/file
git rebase --continue

# اگر می‌خواهی عملیات Rebase را لغو کنی:
git rebase --abort
قانون ایمنی Rebase

Rebase را معمولاً روی Branch شخصی که هنوز دیگران بر اساس Commitهایش کار نمی‌کنند انجام بده. روی Branch مشترک یا Commitهای Pushشده، Rebase بدون هماهنگی می‌تواند تاریخچهٔ دیگران را دچار مشکل کند و گاهی به Force Push نیاز می‌شود. Rebase راه جادویی برای حذف Conflict نیست؛ تعارض ممکن است هنگام اعمال دوبارهٔ هر Commit رخ دهد.

Merge را روی شاخهٔ مقصد اجرا کن.

برای ادغام feature در main: اول git status، سپس git switch main و در پایان git merge feature/search. دستور Merge شاخهٔ نام‌برده را به شاخهٔ فعلی وارد می‌کند، نه برعکس. در تیم‌هایی که روی شاخهٔ شخصی Rebase را ترجیح می‌دهند، ابتدا سیاست تیم را رعایت کن.

Merge Conflict: چرا Git تصمیم نمی‌گیرد؟

تعارض معمولاً وقتی رخ می‌دهد که تغییرات دو مسیر کاری را نتوان بدون ابهام با هم ادغام کرد. این خطا نشانهٔ «خراب بودن Git» نیست؛ Git دربارهٔ نیت برنامه‌نویس‌ها اطلاعات کافی ندارد.

علت ۱

ویرایش یک بخش مشابه

دو Branch یک خط یا بخش نزدیک را به روش ناسازگار تغییر داده‌اند.

حذف در برابر ویرایش

در یک شاخه فایل حذف شده، در شاخهٔ دیگر همان فایل تغییر کرده است.

هر دو شاخه از نقطه‌ای مشترک جدا شده‌اند و پس از آن تغییرهای متفاوتی گرفته‌اند.

روند امن رفع Conflict

  1. ۱
    وضعیت را ببین

    git status فایل‌های حل‌نشده و عملیاتی که متوقف شده‌اند را نشان می‌دهد.

  2. ۲
    نسخه‌ها را بررسی کن

    تفاوت هر دو تغییر را بفهم؛ در صورت نیاز از git diff استفاده کن یا با هم‌تیمی هماهنگ شو.

  3. ۳
    محتوای نهایی را ویرایش کن

    کد درست را نگه دار یا هر دو تغییر را با هم ترکیب کن. نشانگرهای Conflict را حذف کن.

  4. ۴
    فایل حل‌شده را Stage کن

    git add path/to/file به Git اعلام می‌کند تعارض این فایل را حل کرده‌ای.

  5. ۵
    عملیات را کامل و بررسی کن

    در Merge معمولی با git commit ادغام را نهایی کن (اگر Git خودش Commit ساخته باشد، ممکن است لازم نباشد). تست کن و دوباره git status بزن.

اگر می‌خواهی از Merge معمولی منصرف شوی: دستور git merge --abort معمولاً تلاش می‌کند وضعیت قبل از Merge را بازگرداند. اگر از پیش تغییرات محلی داشته‌ای، تضمین نمی‌شود همه‌چیز دقیقاً مثل ابتدا برگردد؛ از وضعیت‌های مهم نسخهٔ پشتیبان داشته باش و پیش از شروع Merge وضعیت را بررسی کن.
پرسش کلاسیاگر دو نفر دو بخش کاملاً جدا از یک فایل را تغییر دهند، حتماً Conflict رخ می‌دهد؟

خیر. Git معمولاً می‌تواند تغییرهای مستقل را ادغام کند؛ تعارض بیشتر وقتی ایجاد می‌شود که نتواند تغییرهای ناسازگار را خودکار حل کند. حتی Merge بدون Conflict هم ممکن است باگ منطقی ایجاد کند.

Conflict در کار تیمی: به‌جای جنگیدن با Git، هماهنگ شوید

قبل از ادغام

کد را در Branch مستقل نگه دارید، Pull Request کوچک بسازید، با git fetch از وضعیت Remote آگاه شوید و تست‌ها را اجرا کنید.

هنگام تعارض

با نویسندهٔ تغییر دیگر دربارهٔ رفتار موردنظر صحبت کنید. انتخاب کورکورانهٔ “ours” یا “theirs” ممکن است منطق برنامه را خراب کند.

پس از حل

نشانگرها را حذف کنید، git diff را بررسی کنید، تست را اجرا کنید، git status را ببینید و بعد Merge را نهایی کنید.

git merge --abort چه زمانی؟

وقتی Merge متوقف شده و می‌خواهی آن عملیات را لغو کنی، می‌توانی از git merge --abort استفاده کنی. این دستور تلاش می‌کند وضعیت پیش از شروع Merge را بازگرداند؛ وقتی از ابتدا تغییرهای محلی ثبت‌نشده داشته‌ای، ممکن است نتواند همه‌چیز را دقیقاً به حالت قبلی برگرداند. برای همین قبل از Merge وضعیت را بررسی کن و تغییرهای مهم را Commit یا Stash کن.

Rollback؛ وقتی نسخهٔ جدید در Production مشکل دارد

Rollback یعنی برگرداندن سرویس به وضعیت پایدار قبلی یا خنثی‌کردن اثر نسخهٔ مشکل‌دار. در Git، راه رایج برای خنثی کردن یک Commit منتشرشده git revert است؛ اما بازگردانی کامل یک Deployment ممکن است به ابزار انتشار، تنظیمات و پایگاه داده هم وابسته باشد.

v1نسخهٔ پایدارCommit A
→
F1جست‌وجوCommit B
→
F2پرداختCommit C
→
F3تغییر باگ‌دارCommit D · Deploy
↘
RRevert DCommit جدید و معکوس

فرض کن سه قابلیت در چند Commit منتشر شده‌اند و پس از Deploy مشخص می‌شود Commit D مشکل را ایجاد کرده است. معمولاً باید Commit معیوب را دقیق شناسایی کنی، اثر معکوس بسازی، تست و Review انجام بدهی و سپس آن اصلاح را منتشر کنی. برای حادثهٔ فوری، سیاست تیم دربارهٔ Rollback مستقیم یا Hotfix را دنبال کن.

git revert <commit-id>

git status
git log --oneline --graph --decorate -10

# هش Commit معیوب را از Log بردار
git revert abc1234

# پیام پیش‌فرض را بررسی/ویرایش و نتیجه را تست کن
git status
git show --stat HEAD

قبل از Revert

A — B — C — D (باگ)

Commit D در تاریخچه وجود دارد و ممکن است قبلاً روی GitHub یا Production رفته باشد.

بعد از Revert

A — B — C — D — R

Commit جدید R اثر D را معکوس می‌کند. D حذف نمی‌شود؛ تاریخچه نشان می‌دهد چه اتفاقی افتاده و چطور جبران شده است.

چرا Revert در شاخهٔ مشترک مناسب‌تر است؟

01تاریخچه حفظ می‌شود

revert Commit قبلی را حذف یا شناسه‌اش را عوض نمی‌کند؛ یک Commit جدید می‌سازد.

02برای Review شفاف است

پیام Commit باید توضیح دهد چه تغییری خنثی می‌شود و چرا؛ مثال: revert: roll back payment redirect regression.

03برای تیم قابل پیگیری است

همکاران می‌توانند ببینند نسخهٔ مشکل‌دار چه بوده و چه اصلاحی انجام شده است.

چند هشدار عملی

قبل از Revert، با git show <hash> مطمئن شو Commit درست را انتخاب کرده‌ای. معمولاً Working Tree باید تمیز باشد. اگر Revert تعارض ایجاد کرد، Conflict را مانند سایر عملیات‌ها حل کن. برای Revert کردن یک Merge Commit، گزینهٔ -m لازم است و باید Parent درست را بفهمی؛ این حالت را بدون مطالعه یا همراهی هم‌تیمی امتحان نکن.

اگر Deploy شامل Migration پایگاه داده، تغییر Schema، پیام صف یا دادهٔ ناسازگار باشد، Revert کردن کد به‌تنهایی لزوماً سرویس را به وضعیت سالم برنمی‌گرداند. به برنامهٔ Rollback، سازگاری نسخه و پشتیبان داده نیز نیاز داری.

مخزن Git تاریخچهٔ نسخه‌ها را نگه می‌دارد؛ GitHub لایه‌ای برای همکاری، بررسی، مدیریت کار و انتشار مستندات یا سایت است.

01

Repository

خانهٔ پروژه است؛ می‌تواند Public یا Private باشد. در مخزن معمولاً کد، README، مجوز، فایل‌های تنظیم و Issueها قرار می‌گیرند.

02

README.md

صفحهٔ معرفی پروژه: چه کاری انجام می‌دهد، چگونه نصب و اجرا می‌شود، پیش‌نیازها چیست و چطور می‌توان مشارکت کرد.

03

.gitignore

قواعدی برای فایل‌هایی که نباید به‌طور عادی به‌عنوان فایل‌های قابل‌ردیابی اضافه شوند؛ مثل محیط مجازی، فایل‌های موقت یا کلیدهای محلی. اگر فایلی قبلاً Track شده باشد، اضافه‌کردن آن به gitignore به‌تنهایی از Track خارجش نمی‌کند.

04

Issues

برای ثبت باگ، پیشنهاد قابلیت، سؤال یا کار قابل پیگیری. می‌توان آن را برچسب‌گذاری و به افراد واگذار کرد.

Fork، Clone و Pull Request چه تفاوتی دارند؟

AFork

ساخت کپی تحت حساب/فضای خودت از یک مخزن در GitHub؛ معمولاً برای مشارکت در پروژه‌ای که اجازهٔ Push مستقیم نداری.

BClone

گرفتن نسخهٔ محلی مخزن برای کار روی رایانهٔ خودت.

CPull Request

پیشنهاد ادغام تغییرها از یک Branch به Branch دیگر، همراه امکان بحث و Code Review.

Pull Request با git pull فرق دارد.

git pull یک دستور Git برای دریافت و ادغام تغییرات Remote است. Pull Request یک قابلیت همکاری در GitHub برای پیشنهاد و بررسی تغییرات است.

قبل از شروع کار تیمی: Fetch یا Pull؟

git fetch origin

Commitها و اطلاعات تازهٔ Remote را می‌گیرد و Remote-tracking refها مثل origin/main را به‌روز می‌کند. شاخهٔ محلی فعلی را خودکار Merge یا Rebase نمی‌کند؛ بنابراین راه کم‌ریسکی برای بررسی وضعیت جدید است.

git status
git fetch origin
git log --oneline --graph --decorate HEAD..origin/main

git pull

در اصل Fetch به‌علاوهٔ ادغام تغییرهاست؛ روش ادغام می‌تواند Merge یا Rebase باشد و به گزینه‌ها/تنظیمات بستگی دارد. اگر Working Tree تغییرهای مبهم دارد، اول آن را مرتب کن. اجرای Pull بدون فهمیدن اثرش ممکن است Merge یا Conflict غیرمنتظره بسازد.

git status
# در workflow ساده، اگر فقط جلو رفتن مجاز است:
git pull --ff-only

# اگر تیم Rebase را برای شاخهٔ شخصی ترجیح می‌دهد:
# git pull --rebase
توصیهٔ دقیق‌تر از «هر بار هر دو را بزن»

در آغاز یک نوبت کار تیمی، ابتدا git status بزن و سپس وضعیت Remote را با git fetch تازه کن. بعد طبق سیاست تیم تصمیم بگیر Merge، Pull یا Rebase انجام بدهی. git pull خودش Fetch دارد؛ معمولاً لازم نیست بلافاصله قبلش یک Fetch تکراری اجرا کنی. همگام‌سازی منظم خوب است، اما هرگز کورکورانه یا بدون دیدن وضعیت محلی Pull نکن.

git remote show و git remote update

git remote -v
git remote show origin
git remote update

# ابتدا فقط پیش‌نمایش پاک‌سازی refهای منسوخ
 git remote prune --dry-run origin
# سپس در صورت اطمینان، پاک‌سازی واقعی
git remote prune origin
git remote show origin

اطلاعات Remote، URLها، Branchهای دنبال‌شده و تنظیمات pull/push را نمایش می‌دهد؛ در صورت اتصال، ممکن است وضعیت شاخه‌ها را هم مقایسه کند.

git remote update

اطلاعات را از Remoteهای تنظیم‌شده (یا گروه مشخص‌شده) Fetch می‌کند؛ تغییرها را داخل شاخهٔ جاری ادغام نمی‌کند.

git remote prune origin

Remote-tracking refهای منسوخ مربوط به شاخه‌هایی را پاک می‌کند که از Remote حذف شده‌اند؛ شاخهٔ محلی واقعی را حذف نمی‌کند. با git remote prune --dry-run origin ابتدا فقط پیش‌نمایش بگیر.

دستورات Remote پرکاربرد

git remote -v

آدرس Remoteهای ثبت‌شده را نشان می‌دهد.

git clone <url>

مخزن را دریافت و یک پوشهٔ کاری محلی ایجاد می‌کند.

git fetch origin

اطلاعات و Commitهای جدید Remote را می‌گیرد؛ ادغام در شاخهٔ فعلی را خودکار انجام نمی‌دهد.

git pull

تغییرات Remote را می‌گیرد و طبق تنظیمات، Merge یا Rebase انجام می‌دهد. پیش از استفاده، وضعیت فایل‌های محلی را ببین.

git push -u origin feature/login

-u یا --set-upstream شاخهٔ راه دور بالادست را تنظیم می‌کند؛ Pushهای بعدی ساده‌تر می‌شوند.

◎حساب شخصی یا Organization؟

برای پروژهٔ شخصی، مخزن معمولاً زیر حساب خودت است. Organization فضای مشترکی برای تیم یا شرکت فراهم می‌کند؛ می‌توان اعضا را به تیم‌ها تقسیم کرد و دسترسی هر تیم به مخزن‌ها را مدیریت کرد. در پروژه‌های گروهی، دسترسی لازم را بده؛ نه بیشتر از نیاز.

↻GitHub Actions چیست؟

ابزاری برای خودکار کردن کارها مثل اجرای تست، بررسی کیفیت کد یا انتشار سایت در واکنش به Push و Pull Request است. تنظیمات معمولاً در فایل‌های YAML زیر مسیر .github/workflows/ قرار می‌گیرند؛ برای این ارائه دانستن کاربردش کافی است.

origin و main چه هستند؟

origin نام پیش‌فرض و رایج یک Remote است، نه کلمه‌ای جادویی؛ می‌توان نام دیگری انتخاب کرد. main هم نام متداول شاخهٔ اصلی است. برای اتصال پروژهٔ محلی به مخزن GitHub معمولاً یک بار git remote add origin <url> اجرا می‌شود؛ پیش از تکرار آن git remote -v را بررسی کن.

اطلاعات حساس را به مخزن نفرست.

رمز عبور، API token، فایل .env واقعی و کلید خصوصی نباید در مخزن Commit شوند. Public بودن مخزن یعنی محتوا برای عموم قابل مشاهده است. اگر Secret را Push کردی، صرفاً حذف فایل از Commit بعدی کافی نیست؛ Secret را فوراً باطل/تعویض کن و طبق نیاز تاریخچه را پاک‌سازی کن.

فصل 11 / شناخت پلتفرمGitHub۷ دقیقه

GitHub یک پلتفرم برای ساختن و همکاری است

Git تاریخچهٔ فایل‌ها و Commitها را مدیریت می‌کند؛ GitHub علاوه بر میزبانی مخزن Git، ابزارهایی برای گفت‌وگو، مدیریت کار، بازبینی کد، خودکارسازی، انتشار و پیدا کردن پروژه‌های دیگران دارد. همهٔ این امکانات وابسته به اجرای دستور Git نیستند.

01

صفحهٔ اصلی و Search

در Home فعالیت‌ها و مخزن‌هایی را که دنبال می‌کنی می‌بینی. نوار Search برای پیدا کردن Repository، کد، Issue، Pull Request، کاربر و Organization است. از فیلترها برای محدود کردن نتیجه استفاده کن.

02

پروفایل شخصی

پروفایل جایی است که دیگران نام، معرفی، پروژه‌های مهم و فعالیت عمومی تو را می‌بینند. README پروفایل و مخزن‌های Pin شده می‌توانند نمونه‌کارهایت را نشان دهند؛ اطلاعات حساس یا شخصی را عمومی نکن.

03

صفحهٔ Repository

در Code فایل‌ها، Branchها، Commitها و README را می‌بینی. معمولاً تب‌های Issues، Pull requests، Actions، Projects، Wiki، Security و Insights هم وجود دارند؛ نمایش همهٔ تب‌ها به نوع مخزن، دسترسی‌ها و فعال‌بودن قابلیت بستگی دارد.

04

Release و Tags

Tag به یک نقطهٔ تاریخچه نام می‌دهد؛ Release معمولاً نسخهٔ قابل استفاده را با توضیحات، تغییرات و گاهی فایل‌های آمادهٔ دریافت معرفی می‌کند. برای فهم وضعیت نسخهٔ پایدار، بخش Releases را بررسی کن.

05

Actions و Projects

Actions می‌تواند تست و کارهای خودکار را اجرا کند. Projects برای مدیریت کارها با Viewهایی مثل Table و Board است و می‌تواند Issueها و Pull Requestها را کنار هم نمایش دهد.

برای دیدن مخزن‌هایی که در بازهٔ زمانی انتخاب‌شده بیشتر مورد توجه قرار گرفته‌اند؛ می‌توانی زبان برنامه‌نویسی و بازهٔ روزانه/هفتگی/ماهانه را هم فیلتر کنی. محبوبیت مقطعی الزاماً به معنی مناسب بودن برای پروژهٔ تو نیست.

چطور یک Repository ناشناس را بررسی کنیم؟

  1. README را بخوان: پروژه چه کاری انجام می‌دهد و چطور نصب و اجرا می‌شود؟
  2. مجوز پروژه (License) را پیدا کن؛ Public بودن به معنی اجازهٔ استفاده از هر نوع کپی‌رایت یا برند نیست.
  3. فایل‌های مهم و زبان‌ها را بررسی کن؛ عدد زبان‌ها فقط سرنخ است، نه ارزیابی کیفیت.
  4. آخرین Commitها، Releaseها و تاریخچهٔ تغییرات را ببین؛ پروژه ممکن است فعال، کم‌فعال یا متوقف شده باشد.
  5. Issueها و Pull Requestهای باز را بخوان تا بفهمی باگ‌ها و بازخوردها چگونه مدیریت می‌شوند.
  6. اگر Actions یا CI دارد، نتیجهٔ تست‌ها را بررسی کن؛ موفق بودن یک اجرا تضمین بی‌نقص بودن برنامه نیست.
  7. قبل از مشارکت، راهنمای CONTRIBUTING.md و قوانین پروژه را بخوان؛ فقط اگر مجوز و شرایط مناسب‌اند، تغییر پیشنهاد کن.

Issue؛ جایی برای تعریف و پیگیری کار

Issue فقط برای باگ نیست؛ می‌تواند سؤال، پیشنهاد قابلیت، کار فنی یا بازخورد باشد. Issue مسئله را دنبال می‌کند؛ Commit تغییر را در تاریخچه ثبت می‌کند؛ Pull Request تغییر را برای بررسی و ادغام پیشنهاد می‌دهد.

چطور از UI یک Issue درست بسازیم؟

  1. وارد صفحهٔ مخزن شو و تب Issues را باز کن؛ سپس New issue را بزن. اگر Issueها در این مخزن غیرفعال‌اند یا دسترسی نداری، امکان ساختن Issue نداری.
  2. عنوان کوتاه و مشخص بنویس؛ مثلاً Bug: empty search query returns 500، نه «مشکل دارد».
  3. در متن توضیح بده چه اتفاقی افتاده، انتظار چه بوده و چطور می‌توان مشکل را دوباره ایجاد کرد.
  4. در بخش کناری، در صورت نیاز Labels، Assignees، Projects، Milestone و نوع Issue را انتخاب کن. همهٔ این گزینه‌ها در همهٔ مخزن‌ها فعال نیستند.
  5. Submit new issue را بزن. بعداً می‌توانی با Commentها توضیح اضافه کنی، سؤال بپرسی یا وضعیت را به‌روز کنی.

الگوی خوب برای گزارش باگ

## What happened?
شرح کوتاه اتفاقی که افتاد

## Expected behavior
انتظار داشتم چه اتفاقی بیفتد؟

## Steps to reproduce
1. این صفحه را باز کن
2. مقدار خالی وارد کن
3. دکمه را بزن

## Environment
OS / Browser / App version

## Logs or screenshots
اطلاعات لازم، بدون رمز، Token یا دادهٔ شخصی

چطور به Issue دیگران پاسخ بدهیم؟

اگر گزارش‌دهنده هستی

به پرسش‌های سازنده پاسخ بده، مراحل بازتولید را دقیق کن، نسخهٔ نرم‌افزار و پیام خطا را اضافه کن و وقتی مشکل برطرف شد نتیجه را تأیید کن. برای کمک، رمز یا Token واقعی را در Issue عمومی نگذار.

Thanks for looking into this.
I can reproduce it on version 1.2.0.
Steps: ...
Expected: ...
Actual: ...

اگر نگه‌دارندهٔ پروژه هستی

با احترام پاسخ بده؛ مشخص کن مشکل را تأیید کرده‌ای یا به اطلاعات بیشتر نیاز داری. اگر تکراری است به Issue اصلی لینک بده. اگر اصلاحی در راه است، Branch یا Pull Request مرتبط را وصل کن.

Thanks for reporting this.
I can reproduce the issue.
Could you share the app version and steps?
Please remove secrets from logs.

ارتباط Issue، Branch، Commit و Pull Request

داخل Commentهای UI می‌توانی با نوشتن #42 به Issue شمارهٔ ۴۲ در همان مخزن اشاره کنی. این کار برای پیدا کردن بحث مرتبط است؛ به‌تنهایی به معنی حل شدن Issue نیست.

در عنوان Commit، شمارهٔ Issue را می‌توان برای زمینه آورد:

fix: handle empty search query (#42)

این عنوان Issue را قابل‌ردیابی می‌کند، اما برای بستن خودکار از واژهٔ بستن استفاده کن. روش پیشنهادی این است که توضیح Pull Request به شکل زیر باشد:

Fixes #42

## What changed?
Handle an empty search query without raising an error.

## Tests
- Added a test for an empty query
- Ran the related test suite

واژه‌های close، closes، closed، fix، fixes، fixed، resolve، resolves و resolved پشتیبانی می‌شوند. مثلاً Closes #42 یا Fixes #42. اگر Issue در مخزن دیگری است، قالبی مانند Fixes OWNER/REPOSITORY#42 را به‌کار ببر.

نکتهٔ دقیق دربارهٔ بستن خودکار

برای گردش کار معمول، عبارت Fixes #42 را در توضیح Pull Request بگذار و PR را به شاخهٔ پیش‌فرض (معمولاً main) هدف بگیر؛ با Merge شدن آن PR، Issue بسته می‌شود. واژهٔ بستن در پیام Commit هم می‌تواند Issue را ببندد، وقتی آن Commit به شاخهٔ پیش‌فرض ادغام شود. نوشتن صرفِ #42 ارجاع می‌سازد، اما به‌تنهایی Issue را نمی‌بندد.

Issue با Pull Request چه فرقی دارد؟

Issue

«چه مشکلی داریم یا چه کاری باید انجام شود؟» محل ثبت مسئله، پرسش و گفت‌وگو.

Pull Request

«چه تغییری پیشنهاد می‌کنم؟» محل مرور Diff، نظر دادن روی کد، بررسی تست‌ها و تصمیم برای Merge.

Project

«چند کار چه وضعیتی دارند؟» نمای مدیریت و اولویت‌بندی Issueها و PRهای متعدد.

فصل 13 / اتصال مخزن‌هاGit + GitHub۸ دقیقه

Remote چیست و چرا فقط یک آدرس ساده نیست؟

Remote یک نام محلی برای آدرس یک مخزن دیگر است. معمولاً این مخزن روی GitHub است، اما می‌تواند روی GitLab، سرور شخصی یا حتی یک مسیر دیگر روی دیسک هم باشد. هر مخزن محلی می‌تواند صفر، یک یا چند Remote داشته باشد.

01

origin

نام قراردادی و رایج Remote اصلی است. وقتی از GitHub مخزنی را با git clone دریافت می‌کنی، Git معمولاً Remote همان مخزن را با نام origin ثبت می‌کند. این نام اجباری نیست.

02

upstream

در کار با Fork، معمولاً origin به Fork زیر حساب خودت و upstream به مخزن اصلی پروژه اشاره می‌کند. این هم یک قرارداد رایج است، نه نامی ویژه در Git.

03

Remote-tracking Branch

نامی مانند origin/main تصویری از وضعیت آخرین Fetch شدهٔ شاخهٔ main در Remote است. خود این نام Branch محلی برای ویرایش مستقیم نیست.

04

Upstream Branch

شاخه‌ای در Remote که Branch محلی با آن ارتباط دارد؛ تنظیم آن کمک می‌کند بدون نوشتن نام Remote و Branch در هر بار Push/Pull، فرمان ساده‌تری اجرا کنی.

فهرست و بررسی Remoteها

git remote
 git remote -v
 git remote show origin
 git branch -r
 git branch -vv
git remote

فقط نام Remoteهای ثبت‌شده را نشان می‌دهد.

git remote -v

آدرس Fetch و Push هر Remote را نمایش می‌دهد؛ برای بررسی اشتباه بودن URL بسیار مفید است.

git remote show origin

اطلاعات Remote و شاخه‌های مرتبط را نشان می‌دهد؛ در صورت نیاز اطلاعات جدیدی را هم پرس‌وجو می‌کند.

git branch -r

Remote-tracking Branchهای شناخته‌شده را فهرست می‌کند.

git branch -vv

برای شاخه‌های محلی، upstream تنظیم‌شده و وضعیت جلو/عقب بودن را نشان می‌دهد، بر اساس آخرین اطلاعات دریافت‌شده.

git fetch --all

از Remoteهای تنظیم‌شده اطلاعات دریافت می‌کند؛ خودش تغییرها را در شاخهٔ فعلی ادغام نمی‌کند.

افزودن، اصلاح، تغییر نام و حذف یک Remote

# افزودن Remote
 git remote add origin https://github.com/USERNAME/REPOSITORY.git

# اصلاح URL موجود
 git remote set-url origin git@github.com:USERNAME/REPOSITORY.git

# تغییر نام Remote
 git remote rename origin personal

# حذف آدرس از پیکربندی محلی
 git remote remove personal

# بررسی نتیجه
 git remote -v
حذف Remote، Repository روی سایت را حذف نمی‌کند.

git remote remove origin فقط اتصال ذخیره‌شده در مخزن محلی تو را پاک می‌کند. Repository روی GitHub همچنان باقی می‌ماند. برای حذف مخزن آنلاین باید از UI سایت و با دقت جداگانه اقدام کرد.

سناریوی مهم: همگام شدن با مخزن اصلی پس از Fork

وقتی پروژهٔ شخص دیگری را Fork کرده‌ای، می‌خواهی تغییرهای جدید مخزن اصلی را هم دریافت کنی. ابتدا آدرس واقعی مخزن اصلی را جایگزین کن:

# origin معمولاً به Fork خودت وصل است
git remote -v

# فقط یک بار آدرس مخزن اصلی را ثبت کن
git remote add upstream https://github.com/ORIGINAL_OWNER/PROJECT.git

# اطلاعات جدید مخزن اصلی را بگیر
git fetch upstream

# اگر تیم چنین روشی را تأیید می‌کند، تغییرها را روی main محلی ادغام کن
git switch main
git merge upstream/main

# در صورت نیاز، main به‌روز شده را به Fork خودت بفرست
git push origin main

اگر مخزن اصلی یا Fork شما از نام شاخه‌ای غیر از main استفاده می‌کند، نام درست را جایگزین کن. در پروژهٔ واقعی، پیش از Merge کردن تغییرهای upstream، وضعیت محلی و راهنمای مشارکت پروژه را بخوان.

اشتباه‌های رایج Remote و راه تشخیص

خطا ۱

remote origin already exists

Remote با نام origin قبلاً ثبت شده است.

راه‌حل
git remote -v

اگر URL غلط است از git remote set-url origin NEW_URL استفاده کن؛ اگر درست است نیازی به افزودن دوباره نیست.

خطا ۲

Repository not found

URL، نام مالک/مخزن، دسترسی یا احراز هویت ممکن است مشکل داشته باشد.

راه‌حل
git remote -v

URL صفحهٔ مخزن را بررسی کن و مطمئن شو اجازهٔ دسترسی داری. اگر Private است، باید با حساب مجاز و روش احراز هویت مناسب وصل شوی.

خطا ۳

rejected (fetch first)

Remote تغییرهایی دارد که مخزن محلی هنوز دریافت نکرده است.

راه‌حل
git status
git fetch origin
git log --oneline --graph --decorate HEAD..origin/main

تفاوت‌ها را بررسی کن، تغییر محلی را حفظ کن و طبق سیاست تیم همگام شو. برای رفع این خطا بدون بررسی، Force Push نزن.

قانون ساده برای کار با Remoteها

fetch اطلاعات را می‌آورد؛ pull دریافت را با Merge یا Rebase ترکیب می‌کند؛ push Commitهای محلی را به Remote می‌فرستد. اگر مطمئن نیستی ابتدا git status و git remote -v بزن و بعد تصمیم بگیر.

فصل 14 / مسیر عملی کاملGit + GitHub۱۰ تا ۱۵ دقیقه

از صفر تا تغییر یک پروژه؛ قدم‌به‌قدم

این فصل را مثل یک اجرای زنده ارائه کن. اول حساب GitHub می‌سازیم، بعد یک Repository می‌سازیم، آن را روی کامپیوتر می‌گیریم، یک فایل را تغییر می‌دهیم و تغییر را با Commit و Push به GitHub می‌فرستیم.

فرق ابزارها را در طول مسیر مشخص نگه دار

ساخت حساب و Repository در سایت، کار GitHub است. ویرایش فایل، بررسی تغییر، Stage و Commit روی کامپیوتر با Git انجام می‌شود. Clone و Push ارتباط بین Git محلی و GitHub را برقرار می‌کنند.

مرحلهٔ ۱ — ساخت حساب GitHub

  1. به github.com/signup برو و مراحل ساخت حساب را انجام بده.
  2. ایمیل را تأیید کن و اگر سایت تأیید امنیتی خواست، مراحل را کامل کن.
  3. نام کاربری را با دقت انتخاب کن؛ معمولاً در URL پروفایل و پروژه‌ها دیده می‌شود.
  4. برای امنیت، رمز منحصربه‌فرد و در صورت امکان Passkey یا Two-factor authentication فعال کن.
یادآوری

رمز حساب GitHub را داخل دستورهای Git، کد یا فایل پروژه قرار نده. git config user.name و user.email اطلاعاتی هستند که در Commit ثبت می‌شوند؛ آن‌ها نام کاربری و رمز ورود GitHub نیستند.

مرحلهٔ ۲ — ساخت Repository روی GitHub

  1. پس از ورود، از دکمهٔ New repository استفاده کن.
  2. نامی ساده مانند git-class-demo انتخاب کن.
  3. برای تمرین کلاسی، Public یا Private را آگاهانه انتخاب کن. Public یعنی دیگران می‌توانند محتوای مخزن را ببینند.
  4. برای ساده نگه‌داشتن اولین تمرین، می‌توانی README را در همان صفحه بسازی؛ این کار یک Commit اولیه روی GitHub ایجاد می‌کند.
  5. دکمهٔ Create repository را بزن و URL مخزن را کپی کن.

اگر Repository را همراه README ساخته‌ای، آن را Clone کن؛ این مسیر برای شروع ساده‌تر است. اگر مخزن خالی ساخته‌ای، می‌توانی یک پوشهٔ محلی را با git init آغاز و سپس Remote را اضافه کنی.

مرحلهٔ ۳ — نصب و بررسی Git روی کامپیوتر

در Windows می‌توانی PowerShell یا Git Bash باز کنی؛ در macOS و Linux از Terminal استفاده کن.

git --version
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --list --show-origin

نام و ایمیل نمونه را با اطلاعات خودت عوض کن. این تنظیمات معمولاً یک بار برای هر حساب کاربری سیستم انجام می‌شوند؛ در پروژهٔ خاص می‌توان تنظیم محلی متفاوت داشت.

مرحلهٔ ۴ — Clone کردن Repository

git clone https://github.com/USERNAME/git-class-demo.git
cd git-class-demo
git status

به‌جای USERNAME نام کاربری خودت و به‌جای نام مخزن، URL واقعی را بگذار. clone فایل‌های پروژه و تاریخچهٔ Git را به کامپیوتر می‌آورد و معمولاً Remote با نام origin را تنظیم می‌کند.

مرحلهٔ ۵ — یک تغییر واقعی ایجاد کن

فایل README.md را با ویرایشگر باز کن و یک خط اضافه کن؛ مثلاً این پروژه برای تمرین Git در کلاس ساخته شده است. سپس ترمینال را باز کن:

git status
git diff

git status می‌گوید کدام فایل تغییر کرده؛ git diff نشان می‌دهد دقیقاً چه خطی حذف یا اضافه شده. اینجا از دانشجوها بپرس: «هنوز چیزی روی GitHub فرستاده‌ایم؟» پاسخ: خیر، فقط فایل محلی تغییر کرده است.

مرحلهٔ ۶ — Stage و Commit

git add README.md
git diff --staged
git status
git commit -m "docs: update project README"
git log --oneline -5

git add تغییر را برای Commit بعدی انتخاب می‌کند. git diff --staged آخرین بار تغییر آمادهٔ ثبت را نشان می‌دهد. git commit آن را در تاریخچهٔ محلی ثبت می‌کند؛ هنوز به GitHub ارسال نشده است.

مرحلهٔ ۷ — Push و بررسی در GitHub

git push

چون مخزن را با git clone گرفته‌ای، معمولاً شاخهٔ محلی از قبل به شاخهٔ Remote وصل است و git push کافی است. اگر Git از تو احراز هویت خواست، از روش امن و مورد پشتیبانی سیستم استفاده کن؛ رمز حساب را در دستور ننویس.

  1. صفحهٔ Repository را در مرورگر Refresh کن.
  2. README را باز کن و خط جدید را ببین.
  3. بخش Commits را باز کن و پیام docs: update project README را پیدا کن.
این نقطهٔ پایان چرخه است

فایل را تغییر دادیم، وضعیت را دیدیم، Diff را بررسی کردیم، تغییر را Stage کردیم، Commit ساختیم و آن را Push کردیم. همین چرخه، پایهٔ بسیاری از کارهای روزمره با Git است.

مرحلهٔ ۸ — تغییر را در Branch جدا انجام بده

git status
git switch -c docs/add-usage
# فایل README.md را تغییر بده
git diff
git add README.md
git diff --staged
git commit -m "docs: add usage instructions"
git push -u origin docs/add-usage

این بار تغییر در Branch جداگانه است. -u شاخهٔ Remote بالادست را تنظیم می‌کند. در GitHub معمولاً دکمهٔ Compare & pull request پیشنهاد می‌شود؛ با آن Pull Request بساز، تغییرها را بررسی کن و پس از Review طبق سیاست پروژه Merge کن.

Commit

تغییر را در تاریخچهٔ محلی ثبت می‌کند.

Push

Commitهای محلی را به Remote می‌فرستد.

Pull Request

در GitHub راهی برای پیشنهاد، بحث و بررسی تغییرها پیش از ادغام است.

اگر پروژه از قبل وجود دارد

اگر قرار است در پروژهٔ موجود مشارکت کنی، اول راهنمای پروژه و دسترسی‌ها را بررسی کن. اگر اجازهٔ Push مستقیم نداری، معمولاً Fork می‌سازی، Fork خودت را Clone می‌کنی، Branch جدا می‌سازی، Commit و Push می‌کنی و سپس Pull Request را به مخزن اصلی پیشنهاد می‌دهی.

سه اشتباه رایج در اجرای زنده

۱) فراموش کردن اینکه Commit محلی است و تا Push روی GitHub نمی‌رود. ۲) Stage کردن فایل‌های حساس مثل .env یا Token؛ پیش از Commit حتماً git status و git diff --staged را ببین. ۳) اجرای git pull کورکورانه وقتی تغییر محلی داری؛ اول git status بزن و روش تیم را رعایت کن.

فصل 15 / تعاملGit + GitHub۵ دقیقه

قبل از جواب، وضعیت را تحلیل کن

این پرسش‌ها را وسط ارائه مطرح کن. برای هر مورد اول از کلاس جواب بگیر و بعد توضیح را باز کن.

آزمون سناریوییسؤال ۱ از ۵
پاسخ‌نامهٔ فعالیت کلاسی (برای مدرس)
  1. فایل را تغییر داده‌ام، اما Add نکرده‌ام. تغییر جدید وارد Commit نمی‌شود؛ Git فقط تغییرهای Stage شده را ثبت می‌کند. برای بررسی: git status و git diff.
  2. Commit کردم ولی Push نکردم. Commit فعلاً در تاریخچهٔ محلی است و لزوماً روی GitHub نیست. برای ارسال، طبق Branch و Remote درست از git push استفاده می‌شود.
  3. چرا Branch جدا می‌سازیم؟ تا قابلیت یا اصلاح از شاخهٔ اصلی جدا باشد، مستقل بررسی شود و بعد از تست با Merge یا Pull Request ادغام شود.
  4. هنگام Merge، دو تغییر ناسازگار داریم. هر دو نسخه را بررسی می‌کنیم، محتوای درست را انتخاب یا ترکیب می‌کنیم، نشانگرهای Conflict را حذف می‌کنیم، فایل را Stage می‌کنیم، تست می‌گیریم و git status را بررسی می‌کنیم.
  5. Commit اشتباه در شاخهٔ مشترک Push شده است. معمولاً git revert <hash> انتخاب امن‌تری است؛ Commit جدیدی می‌سازد که تغییر قبلی را خنثی می‌کند و تاریخچهٔ مشترک را بازنویسی نمی‌کند.

پاسخ سناریوهای اضافه: الف) git restore --staged path/to/file فایل را از Stage خارج می‌کند، بدون اینکه معمولاً تغییر داخل آن را پاک کند. ب) برای Commit اشتباهِ منتشرشده از git revert استفاده کن. ج) پیش از Pull وضعیت را با git status و git diff بررسی و سپس git fetch origin اجرا کن؛ بعد با آگاهی تصمیم بگیر.

سه سناریوی واقعی دیگر

سناریو A

فایل اشتباه Stage شده

هنوز Commit نکرده‌ای و فقط می‌خواهی فایل را از Stage خارج کنی، نه اینکه تغییرهای داخل آن پاک شوند.

راهکار
git restore --staged path/to/file

بعد git status بزن. این کار تغییر را از Stage خارج می‌کند؛ معمولاً فایل را به حالت Modified برمی‌گرداند.

سناریو B

Commit اشتباه قبلاً Push شده

تاریخچه را بازنویسی نکن؛ به‌ویژه وقتی بقیه هم از شاخه استفاده می‌کنند.

راهکار
git log --oneline
git revert <commit-hash>

revert یک Commit جدید می‌سازد که تغییر قبلی را معکوس می‌کند. قبل از اجرا Commit درست را شناسایی کن.

سناریو C

قبل از Pull تغییر محلی داری

نمی‌دانی تغییر محلی با تغییرهای تیم تداخل دارد یا نه.

راهکار
git status
git diff
git fetch origin

اول وضعیت را ارزیابی کن و بعد تصمیم بگیر تغییرها را Commit کنی، موقتاً stash کنی یا به شیوهٔ مناسب دیگری هماهنگ شوی. کورکورانه reset نکن.

سناریوی اضافی: تغییرات نیمه‌تمام را موقتاً کنار بگذارم؟

اگر لازم است موقتاً شاخه را عوض کنی و نمی‌خواهی تغییرهای محلی را همین حالا Commit کنی، بعد از بررسی git status می‌توانی از git stash استفاده کنی. Stash جای Commit دائمی نیست و تغییرهای Untracked هم به‌طور پیش‌فرض ذخیره نمی‌شوند.

git stash push -m "work in progress"
git switch main
# وقتی برگشتی به شاخهٔ کاری:
git switch feature/login
git stash pop

بعد از stash pop دوباره وضعیت را بررسی کن؛ اگر دو تغییر با هم ناسازگار باشند ممکن است Conflict پیش بیاید.

فصل 16 / انتشار در وبGitHub Pages۳ دقیقه

چطور همین وب‌بوک را منتشر کنی؟

این پروژه فقط HTML، CSS و JavaScript سمت مرورگر است؛ برای نمایش آن به سرور Python یا Node.js نیاز نداری. GitHub Pages می‌تواند فایل‌های استاتیک را منتشر کند.

01
مخزن جدید بساز

در GitHub یک Repository بساز. برای ساده‌ترین مسیر می‌توانی آن را Public انتخاب کنی. در استفادهٔ معمول، سایت Pages را عمومی فرض کن؛ خصوصی بودن Repository به‌تنهایی آن را خصوصی نمی‌کند و انتشار خصوصی به پلن و تنظیمات دسترسی وابسته است.

02
فایل‌های پروژه را آپلود کن

index.html، styles.css، script.js و فایل‌های متنی را در ریشهٔ مخزن قرار بده.

03
بخش Pages را باز کن

Repository → Settings → Pages → بخش Build and deployment.

04
منبع انتشار را تنظیم کن

در Source گزینهٔ Deploy from a branch را انتخاب کن؛ Branch را main و پوشه را /(root) قرار بده، سپس Save کن.

05
لینک انتشار را باز کن

پس از پایان Build، آدرس سایت در همان بخش Pages ظاهر می‌شود. اولین انتشار ممکن است چند دقیقه زمان ببرد.

اگر می‌خواهی با ترمینال ارسال کنی

git init -b main
git add .
git status
git commit -m "docs: add Git and GitHub webbook"
git remote add origin https://github.com/USERNAME/REPOSITORY.git
git push -u origin main

ابتدا مخزن خالی را در GitHub بساز و URL واقعی خودت را جایگزین کن. اگر پروژه را از قبل با Git مدیریت می‌کنی، دوباره git init نزن؛ فقط Remote و Push را طبق وضعیت فعلی تنظیم کن.

نکتهٔ مهم امنیتی

GitHub Pages سایت ایستا را منتشر می‌کند؛ برای اجرای کد سمت سرور مثل Django یا PHP نیست. هرگز رمز، token یا اطلاعات خصوصی را داخل این سایت Commit نکن. راهنمای رسمی Pages را در منابع پایین ببین.

فراتر از مبانی

Tag، Alias و Hook؛ سه ابزار مفید

01

Tag؛ علامت‌گذاری نسخه

برای علامت‌گذاری نقطه‌ای مشخص از تاریخچه، مثلاً نسخهٔ انتشار v1.0.0، از Tag استفاده می‌شود. Tag جای Branch را نمی‌گیرد؛ معمولاً برای اشاره به یک نسخهٔ معین به کار می‌رود.

git tag
 git tag -a v1.0.0 -m "Release v1.0.0"
git push origin v1.0.0

گزینهٔ -a یک annotated tag می‌سازد. اگر فقط git push اجرا کنی، Tag جدید لزوماً ارسال نمی‌شود؛ Tag موردنظر را Push کن یا آگاهانه از git push --tags استفاده کن.

02

Alias؛ میان‌بر شخصی

می‌توان برای دستورهای پرتکرار نام کوتاه تعریف کرد؛ این تنظیم به‌صورت پیش‌فرض روی سیستم/حساب خودت باقی می‌ماند.

git config --global alias.st status
git st

Alias جای یادگیری فرمان اصلی را نمی‌گیرد؛ فقط تایپ روزمره را کوتاه می‌کند.

03

Hooks و Attributes

Hook اسکریپتی است که در رویدادی مثل pre-commit اجرا می‌شود. فایل‌های Hook معمولاً داخل .git/hooks مخزن محلی هستند و به شکل عادی همراه Clone به دیگران منتقل نمی‌شوند.

.gitattributes می‌تواند رفتار فایل‌ها را برای Git مشخص کند؛ مثلاً مدیریت پایان خطوط یا تفاوت‌نمایی برخی فایل‌ها.

قانون تیمی را فقط به Hook محلی نسپار. برای بررسی الزامی از CI، تنظیمات حفاظت شاخه یا قواعد مخزن هم استفاده کن.

نکتهٔ نسخه‌گذاری

Branch مسیری برای ادامهٔ کار است؛ Tag معمولاً نامی پایدار برای یک نقطه از تاریخچه، مثل نسخهٔ منتشرشده. این دو کاربرد متفاوتی دارند.
